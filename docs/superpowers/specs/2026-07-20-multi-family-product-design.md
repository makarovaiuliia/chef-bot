# Chef-Bot → мультисемейный продукт (пробный период + платно) — дизайн

**Дата:** 2026-07-20
**Статус:** утверждён пользователем
**Обновлено 2026-07-20 (вечер):** §3, §4, §7 — управление семьёй, инвайты и
планирование только админам; несколько админов (назначение без потери прав у
прежнего); `can_plan` выведен из употребления; зафиксирован жизненный цикл меню;
флоу /plan — под фича-флагом `planning_enabled` (бота можно раздавать до
готовности планирования: семьи грузят меню через /load).
**Контекст:** бот сейчас обслуживает одну семью (allowlist, профиль семьи зашит в
`core/prompts/base_context.md`, меню грузится готовым JSON через `/load`).
Цель — превратить его в self-serve Telegram-бот для планирования семейного меню,
проверить спрос на 20–50 семьях. Модель — **бесплатный пробный период, затем
платно**; сам приём оплаты в этой итерации не строим (см. §6 и роадмап).

## Утверждённые продуктовые решения

1. **Редактируемый блок профиля.** Промпт планирования = фиксированная техническая
   часть (скрыта от юзера, идёт через prompt caching) + текст «профиля семьи»
   (`families.profile_md`), который генерируется из онбординга и свободно
   редактируется юзером. Технические инструкции сломать нельзя.
2. **Пробный период, затем платно.** Без подписки семье доступен разовый
   (пожизненный) пробный лимит; по исчерпании — заглушка «платный доступ скоро».
   Сам приём оплаты в этой итерации не строим (см. §6, роадмап).
3. **Без группировки по магазинам.** Единый список покупок. Enum `Store`
   убирается, колонка `store` становится nullable-строкой (данные не теряются,
   UI не показывает).
4. **Рецепты остаются.** Кнопка «Рецепт» у каждого блюда в `/today` и `/menu`
   (существующий `recipe_service` с кэшированием).
5. **Свободное общение с AI отключено.** Free-text хендлер отвечает подсказкой
   со списком команд. Tool-use агент (`core/services/conversation.py`)
   выключается фича-флагом, не удаляется — кандидат в платный тариф позже.
6. **Postgres с этапа 1.** Managed Postgres (Railway) + `asyncpg`;
   SQLite остаётся для локальной разработки и тестов.

## 1. Путь нового юзера (онбординг)

`/start` без параметров → создаётся семья, юзер становится администратором →
FSM-опрос из 6 шагов, максимум кнопками:

1. Сколько человек (кнопки 1/2/3/4+, уточнение про детей).
2. Какие приёмы пищи планировать — мультивыбор: завтрак / обед / ужин.
   Enum `MealSlot` расширяется значением `breakfast`. Выбор хранится в
   `families.plan_slots` (JSON-список).
3. Аллергии и исключения — кнопки-пресеты (лактоза, глютен, лук/чеснок,
   орехи…) + свой вариант текстом.
4. Лимит активной готовки: 20 / 40 / 60 минут.
5. Предпочтения по белкам и кухне — мультивыбор кнопками + текст.
6. «Что ещё важно?» — свободный текст, можно пропустить. Здесь же город →
   из него таймзона (`families.timezone`).

Из ответов Claude генерирует текст профиля семьи (аналог текущего
`base_context.md`) → показывается юзеру → «✅ Всё верно» / «✏️ Редактировать».
После подтверждения — приглашение к `/plan`.

`/start inv_<код>` → присоединение к существующей семье участником, без
онбординга (см. §4).

## 2. Профиль и промпт

- `/profile` — показать текст профиля; кнопка «Редактировать» → юзер присылает
  новую версию целиком (ForceReply). Редактирует только администратор.
- Промпт планирования собирается как: технический шаблон (JSON-схема ответа,
  правила чередования белков, стиль; в репозитории) + `profile_md` семьи.
- Техническая часть промпта помечается для prompt caching.

## 3. Флоу /plan

Доступен только администраторам семьи (их может быть несколько, см. §4).

1. Дата старта — кнопки: сегодня / завтра / понедельник / своя (ввод даты).
2. Длительность — 3 / 5 / 7 дней. **Жёсткий потолок длительности меню — 14 дней**:
   валидация в `menu_planner` (и в `/load` — суммарный горизонт загружаемого JSON
   не дальше 14 дней вперёд от start_date); при превышении — отказ с пояснением.
   Кнопок длиннее недели в UI нет, потолок страхует кастомные пути (свой ввод,
   /load, будущие фичи).
3. Генерация меню Claude'ом по профилю → черновик (`MenuStatus.draft`).
   Возвращается in-bot генерация: новый сервис `core/services/menu_planner.py`.
4. Показ черновика с кнопками:
   - «🔄 Заменить блюдо» → выбор дня/слота → 2–3 альтернативы от
     `dish_replacer` + вариант «своё пожелание» одной строкой
     (скоуп-ограниченный ввод, не свободный чат);
   - «♻️ Перегенерировать всё» (считается отдельной генерацией в лимитах);
   - «✅ Утвердить» → меню активируется, затем бот **предлагает составить
     список покупок по меню** (кнопка; уточнение 2026-07-21: сборка списка —
     часть планирования, отдельного входа для нее нет, только под утвержденное
     меню). Сборка — отдельная LLM-операция `shopping`: без собственного
     триал-лимита, но под месячным токен-потолком; при сборке закрываются
     устаревшие menu-bound пункты (ручные /add не трогаются).

`/load` (JSON-меню) остаётся как скрытая admin-команда — личный workflow
текущей семьи не ломается.

**Фича-флаг планирования:** весь флоу `/plan` — под флагом `planning_enabled`
(default off). При выключенном флаге `/plan` отвечает заглушкой «планирование
скоро появится», команда не анонсируется в меню команд и `/help`; бот при этом
полноценно работает (онбординг, `/load` админом, покупки, рецепты) — его можно
раздавать семьям до готовности планирования. Включение — env-переменной.

## 4. Семья, администраторы и права

**Роли:** создатель семьи — **администратор** (`role=admin`), остальные —
участники (`role=member`). Администраторов может быть несколько.

**Права администратора:** управление семьёй (`/family` с кнопками), приглашения
(`/invite`), весь доступ к планированию (`/plan`, замены, утверждение меню,
`/load`) и редактирование профиля — только администраторы. Обычный участник
получает эти возможности только когда его назначают администратором.
Флаг `family_members.can_plan` **выведен из употребления** (колонка остаётся в
БД до отдельной чистки, нигде не читается). Участник без прав при `/plan`
получает «Попросите администратора назначить вас администратором» с именами
админов. Просмотр состава семьи в `/family` (без кнопок) доступен всем.

**Инвайты:** `/invite` (только админ) → deep-link `t.me/<bot>?start=inv_<код>`.
Код хранится в `families.invite_code`, можно перевыпустить.

**Уведомления администраторам** (всем админам, кроме автора действия):

- участник присоединился по инвайту;
- участник добавил пункты в список покупок;
- админ сгенерировал или утвердил меню (уведомляются остальные админы).

Уведомления между обычными участниками («N добавил в список») остаются для
всех; админские добавляются поверх, без дублей самому себе.
Настройка `vova_telegram_id` из конфига удаляется.

**Назначение администратора:** в `/family` — «Сделать админом» для участника.
Прежний администратор свои права **не теряет**: передачи роли нет, только
добавление нового админа.

## 5. Напоминания

- Утренний дайджест — становится per-family: `families.timezone`,
  `families.digest_hour`, вкл/выкл в `/settings`. Планировщик остаётся
  asyncio-задачей, но обходит семьи с учётом их локального времени.
- **Новое:** за 2 дня до конца активного меню — «Меню заканчивается,
  спланировать следующее?» с кнопкой, запускающей `/plan` (только тем,
  у кого есть право планировать).

## 6. Пробный период и расходы

Модель: **бесплатный пробный период (триал), затем платно.** Пока у семьи нет
подписки, ей доступен разовый пробный лимит. По исчерпании — заглушка «платный
доступ скоро, напишем вам» (сам биллинг строится отдельно, см. роадмап). Так мы
проверяем спрос и готовность платить, не вкладываясь в оплату на старте.

- Таблица `llm_usage`: family_id, операция (menu_gen / replace / recipe /
  profile), tokens_in/out, created_at.
- **Триал — разовый (пожизненный) лимит на семью**, НЕ ежемесячный сброс
  (константы в конфиге): **4 генерации меню, 15 замен, 15 рецептов**. Считается
  как суммарное число операций по `llm_usage` за всё время (без временного окна —
  проще, чем месячный сброс; логики сброса нет).
- По исчерпании любого лимита — вежливое сообщение: доступ по подписке скоро,
  оставьте заявку / ждите анонса. Кнопки оплаты в MVP нет.
- Генерация профиля в онбординге — 1 раз, вне лимитов.
- Сборка списка покупок (`shopping`) — вне триал-счетчиков (часть планирования,
  доступна только по утвержденному меню), но токены учитываются в месячном
  потолке (уточнение 2026-07-21).
- **Месячный потолок расходов на семью (safety cap)** — независимо от триала и
  будущих подписок: суммарные токены семьи за календарный месяц (SUM по
  `llm_usage.tokens_in + tokens_out` за текущий месяц) не превышают константу
  из конфига (ориентир: `MONTHLY_TOKEN_CAP_PER_FAMILY = 500_000`, ~$2 на Sonnet).
  Проверка перед каждой LLM-операцией; при превышении — вежливый отказ с датой
  сброса (1-е число). Триал ограничивает число операций «на всю жизнь», потолок —
  скорость трат в моменте; для платных тарифов позже это станет anti-abuse
  ceiling. Суперадмин сможет поднять потолок конкретной семье (роадмап).
- Ориентир стоимости всего триала на семью: ~$0.35–0.45 единоразово
  (Sonnet + prompt caching). Основной риск расходов — не активные семьи, а
  масса брошенных после онбординга; профиль генерируется один раз, так что это
  дёшево.
- Суперадмин (оператор продукта) может продлить триал / поднять лимит
  конкретной семье — см. роадмап, §«Суперадмин-панель». В MVP лимиты правятся
  только в конфиге.

## 7. Изменения модели данных

Одна ветка миграций (alembic 0005+):

- `families`: + `profile_md TEXT`, `timezone TEXT` (default UTC),
  `digest_hour INT` (default 9), `digest_enabled BOOL` (default true),
  `plan_slots JSON`, `invite_code TEXT UNIQUE`.
- `family_members`: + `role` (admin/member), `can_plan BOOL default false`
  (can_plan — deprecated с 2026-07-20: права даются только через `role=admin`,
  колонка нигде не читается, удаление — отдельной чисткой).
  У существующих семей первый участник становится admin.
- `meals`: `MealSlot` + `breakfast`.
- `shopping_items`: `store` → nullable String (enum убирается).
- Новая таблица `llm_usage`.
- FSM-состояния онбординга — в памяти aiogram (MemoryStorage), не в БД:
  прерванный онбординг просто начинается заново.

**Жизненный цикл меню:** строки `menus` не удаляются никогда (исключение —
черновики `/plan` до утверждения); меню живёт в БД минимум до конца своего
срока и дальше, прошедшие даты просто выпадают из выборок `date >= today`.
`meals` удаляются только при явно подтверждённой пользователем перезаписи
конфликтных дат (`/load` и утверждение в `/plan`); фоновых чисток нет.

**Переход на Postgres:** зависимость `asyncpg`, managed Postgres на Railway,
`DB_URL=postgresql+asyncpg://…`, прогон миграций 0001–0005. Проверить
совместимость типов (JSON, enum'ы) в существующих миграциях. SQLite остаётся
дефолтом для локальной разработки и тестов.

**Миграция текущей семьи:** скрипт сеидит `profile_md` из `base_context.md`,
назначает админа, `plan_slots=[lunch, dinner]`, `timezone=Asia/Bangkok`.
Allowlist-middleware удаляется.

## 8. Обработка ошибок

- Невалидный JSON от LLM при генерации меню/профиля → один автоматический
  retry, затем дружелюбная ошибка с кнопкой «Попробовать ещё раз»
  (retry считается в лимитах только при успехе).
- Конфликт дат при утверждении (уже есть активное меню на эти даты) —
  существующая логика preview/commit из menu_loader переиспользуется.
- Таймаут генерации → сообщение-плейсхолдер «Готовлю меню…» редактируется
  результатом или ошибкой.

## 9. Тестирование

Существующие паттерны (pytest + pytest-asyncio, unit для чистой логики,
integration с in-memory SQLite для сервисов):

- unit: сборка промпта из профиля, проверка прав (роли/can_plan), расчёт
  лимитов, парсинг ответов menu_planner;
- integration: онбординг-сервис, menu_planner, инвайты/роли, per-family
  дайджест, напоминание о конце меню;
- один smoke-прогон миграций на Postgres (docker) в CI или вручную перед
  деплоем.

## 10. Этапы реализации

1. **Мультитенантное ядро + Postgres:** профиль-как-данные, онбординг,
   инвайты, роли/права, снятие allowlist, миграция 0005, Railway Postgres,
   миграция текущей семьи.
2. **Планирование:** menu_planner, флоу правок (dish_replacer в кнопках)
   и аппрува, потолок длительности меню 14 дней (включая /load), отключение
   free-text агента фича-флагом.
3. **Персонализация:** per-family таймзона/дайджест, напоминание «пора
   планировать», лимиты триала и месячный токен-потолок (llm_usage).
4. **Полировка и запуск беты:** тексты, /help, базовые метрики
   (семьи/генерации/расход токенов), онбординг первых внешних семей.

Каждый этап оставляет бота рабочим для текущей семьи.

## Вне скоупа (следующие итерации)

- Биллинг (Telegram Stars), тарифы.
- Возврат свободного AI-чата как платной фичи.
- Фидбек по блюдам 👍/👎 с дописыванием в профиль.
- Группировка покупок по магазинам семьи.
- Локализация на другие языки.
- Webhook вместо polling, вынос планировщика в очередь задач.
