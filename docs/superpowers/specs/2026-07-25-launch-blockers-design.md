# Блокеры запуска на аудиторию — дизайн

Дата: 2026-07-25. Источник: аудит готовности к публичному запуску. Четыре
изменения, без которых бота нельзя отдавать незнакомым людям, плюс честные
тексты ожидания на всех LLM-вызовах.

Продуктовая база — [multi-family-product-design.md](2026-07-20-multi-family-product-design.md)
(далее «спека»). Решение спеки §4 «передачи роли нет, только добавление нового
админа» **сохраняется**: снятие админки в этот заход не входит.

---

## 1. Выход из семьи и удаление участника

### Проблема

`telegram_user_id` уникален глобально ([db.py](../../../core/db.py) —
`family_members.telegram_user_id unique`), инвайт-ссылка постоянная и
многоразовая, а операций удаления в коде нет вообще. Пересланная ссылка →
посторонний навсегда в семье, видит меню, списки покупок и профиль с
аллергиями. Ни он не уйдёт, ни админ его не выкинет, ни суперадмин не поможет.
Плюс сам пострадавший больше не может создать свою семью (`AlreadyInFamily`).

### Правила

| Действие | Кто | Ограничение |
|---|---|---|
| Покинуть семью | любой участник | Запрещено, если ты единственный админ **и** в семье есть другие участники |
| Удалить участника | админ | Только участников с `role=member`; других админов и себя — нельзя |

«Админ не удаляет админа» — сознательное ограничение: иначе это снятие админки
через чёрный ход (решение спеки §4) плюс сценарий «двое админов выкидывают друг
друга». Себя админ удаляет через «Покинуть семью», а не кнопкой удаления.

Известный незакрытый сценарий: если посторонний успел стать админом, выкинуть
его нельзя. Принято осознанно — назначение админом требует явного действия
существующего админа.

### Крайние случаи

**Ушёл последний человек** (единственный админ, других участников нет).
Блокировка не срабатывает, выход разрешён. Строки `menus` / `meals` /
`shopping_items` не удаляются (спека §7 — «строки menus не удаляются никогда»),
но `families.invite_code` **обнуляется**: по утёкшей ссылке нельзя попасть в
семью без админа. Юзер после выхода делает `/start` и создаёт новую семью —
работает через существующий `no_family_fallback`.

**Ушедший или удалённый пользуется ботом.** Мидлварь не находит семью →
`no_family_fallback` → «Сначала настроим бота: нажмите /start» → онбординг.
Существующее поведение, менять не нужно.

### Схема БД

Не меняется, миграция не нужна. Достаточно удалить строку `family_members`:
`ShoppingItem` привязан к `family_id`, а не к участнику; `ClaudeConversation` и
`SubscriptionRequest` держат `telegram_user_id` без FK.

### Ядро

В [core/services/family_service.py](../../../core/services/family_service.py):

- `leave_family(session, *, family, member) -> None` — кидает
  `LastAdminCannotLeave`, если участник админ, других админов нет и в семье есть
  кто-то ещё. Обнуляет `invite_code`, если ушёл последний участник.
- `remove_member(session, *, family_id, actor, member_id) -> FamilyMember` —
  кидает `MemberNotInFamily` (нет такого или чужая семья), `CannotRemoveAdmin`
  (цель — админ), `CannotRemoveAdmin` же при попытке удалить себя.

Новые исключения в [core/exceptions.py](../../../core/exceptions.py) рядом с
`MemberNotInFamily`, оба наследуют `FamilyError`.

### UI

`/family` глазами админа:

```
Семья «Ивановы»:
👑 Юля
   Петя
   Незнакомец

[👑 сделать админом: Петя]
[🚫 удалить: Петя]
[🚫 удалить: Незнакомец]
[🔄 Новая инвайт-ссылка]
[🚪 Покинуть семью]
```

«Покинуть семью» — в обеих ветках `/family`, и админской, и обычной.

Оба действия необратимы → подтверждение в два шага:
`fam:rm:<member_id>` → «Удалить Петю из семьи? Он потеряет доступ к меню и
спискам покупок.» → `fam:rmyes:<member_id>` / `fam:rmno`.
`fam:leave` → «Покинуть семью «Ивановы»? Вы потеряете доступ к меню и спискам.
Вернуться можно только по новой ссылке-приглашению.» → `fam:leaveyes` /
`fam:leaveno`.

`member_id` едет в `callback_data`, а не во FSM: подтверждение переживает
рестарт бота (FSM в `MemoryStorage` — отдельная известная проблема, здесь её не
задеваем).

### Уведомления

По образцу спеки §4:

- участника удалили → ему: «Вас удалили из семьи «X»»;
- участник ушёл сам → всем админам: «N покинул(а) семью».

Отправка в `try/except` с `logger.warning`, как в существующих
`_notify_admins` / `start_with_invite`.

## 2. Обработчик ошибок и длинные сообщения

### Проблема

`dp.errors` не зарегистрирован. Любое необработанное исключение = молча
проглоченный апдейт, юзер сидит перед «⏳ Готовлю меню...» вечно. Это не
теория: код построен на `placeholder.edit_text(...)`, а `edit_text` кидает
`TelegramBadRequest`, когда сообщение удалено или не изменилось.

Отдельно: нигде нет разбиения по лимиту Telegram в 4096 символов. Вывод
рецепта (`max_tokens=4096` на выходе LLM — это заметно больше 4096 *символов*
русского текста) и список семей в `/admin` могут падать уже сейчас.

### Обработчик

Новый модуль `bot/errors.py`, регистрируется в `create_dispatcher()` —
`main.py` остаётся тонким. Получает `ErrorEvent`, делает три вещи:

1. `logger.exception` с трейсом;
2. отвечает юзеру в тот же чат: «Что-то сломалось, попробуйте ещё раз» плюс
   `cb.answer()` для callback-апдейта, чтобы снять спиннер;
3. алерт суперадминам (`settings.superadmin_ids`): тип исключения, вид апдейта,
   хвост трейса.

Дроссель против шторма: ключ `type(exc).__name__` → время последней отправки,
в памяти процесса, подавление 5 минут. После рестарта дроссель пуст — худший
случай это один лишний алерт, приемлемо.

Обработчик обёрнут так, что не может упасть сам: отправка юзеру тоже падает,
если бот заблокирован.

### Безобидные ошибки Telegram

Не баги, алерт по ним не нужен: `message is not modified`,
`message to edit not found` (юзер удалил сообщение), `query is too old`
(callback старше 48 часов). Для них — только лог уровня INFO, без алерта и без
извинений юзеру. Матчинг по подстроке в тексте `TelegramBadRequest`: отдельных
классов под них в aiogram 3 нет.

### Разбиение

`split_for_telegram(text, limit=4096) -> list[str]` в
[bot/formatting.py](../../../bot/formatting.py), режет по границам строк
(сначала по пустой строке, затем по одиночному переводу). Допущение: HTML-теги
не пересекают перевод строки — для наших форматтеров это так.

Применяется там, где переполнение реально: список семей в `/admin`, вывод
рецепта, `/menu` на длинном меню, список покупок текстом.

## 3. Суточный лимит генерации профиля в онбординге

### Проблема

[limits.py](../../../core/services/limits.py) фиксирует: «генерация профиля в
онбординге сюда не ходит (вне лимитов, семьи ещё нет)». Для закрытой беты
нормально, для открытой аудитории — бесплатный LLM-вызов на аккаунт,
повторяемый бесконечно: пройти опрос → получить профиль → не подтверждать →
`/start` → снова.

### Механика

Новая таблица, миграция `0008`:

```
onboarding_attempts(id PK, telegram_user_id BIGINT NOT NULL, created_at)
```

По строке на попытку. Лимит проверяется как
`COUNT(*) WHERE telegram_user_id = ? AND created_at >= начало сегодняшних
UTC-суток` — тем же приёмом, что уже используют `count_llm_operations` и
`sum_llm_tokens_current_month`. Никакой логики сброса счётчика, никакого нового
словаря состояний.

Конфиг: `onboarding_daily_limit: int = 5`.

Попытка записывается **до** вызова LLM. Токены тратятся даже когда модель
вернула невалидный JSON (`generate_profile` внутри делает retry), а иначе
злоупотребление сводится к «вызывай так, чтобы падало».

### Размещение

`ensure_onboarding_attempt_allowed(session, telegram_user_id)` в
[core/services/onboarding.py](../../../core/services/onboarding.py), кидает
`OnboardingLimitExceeded` — тестируется без Telegram. Хендлеру
`_generate_and_show` нужно протащить `db_session` (сейчас он его не принимает,
хотя мидлварь уже кладёт его в `data`).

Отказ юзеру: «Сегодня уже 5 попыток составить профиль — это защита от
перерасхода. Попробуйте завтра.»

Видимость для оператора: строка «Онбординг сегодня: N попыток» в `/admin`.

## 4. Тексты ожидания на всех LLM-вызовах

### Проблема

Плейсхолдеры не говорят, сколько ждать: «⏳ Готовлю меню...» на генерации
недельного меню и «⏳ Подбираю варианты...» на быстрой замене выглядят
одинаково. А смена таймзоны в [settings.py](../../../bot/handlers/settings.py)
уходит в LLM **вообще без плейсхолдера** — юзер сидит перед пустотой.

### Механика

Таблица в [core/constants.py](../../../core/constants.py). Ключи — существующие
имена операций из `llm_usage`, чтобы не заводить второй словарь:

```python
LLM_WAIT_HINTS = {
    "menu_gen":     "до минуты",
    "shopping":     "до 40 секунд",
    "profile":      "до 40 секунд",
    "recipe":       "до 30 секунд",
    "replace":      "до 20 секунд",
    "conversation": "до 20 секунд",
    "tz_detect":    "пару секунд",
}
```

Ключ `conversation` нужен, хотя свободный чат выключен фича-флагом: гард-тест на
полноту словаря проверяет все места с плейсхолдером, включая это.

Хелпер `wait_text(icon, label, operation) -> str` в `bot/formatting.py` даёт
`"{icon} {label}... ({подсказка})"`.

Точки применения — семь существующих плюс новый плейсхолдер для смены
таймзоны:

| Место | Операция |
|---|---|
| `plan.py` генерация меню | `menu_gen` |
| `plan.py` подбор замен | `replace` |
| `plan.py` список в `/list` | `shopping` |
| `plan.py` список текстом | `shopping` |
| `menu.py` рецепт | `recipe` |
| `onboarding.py` профиль | `profile` |
| `freetext.py` свободный чат (за фича-флагом) | `conversation` |
| `settings.py` смена таймзоны — **новый** | `tz_detect` |

### Кэш рецептов

`get_recipe` отдаёт сохранённый рецепт мгновенно, и тогда «(до 30 секунд)»
мелькнёт и сразу заменится готовым текстом — не ложь, но шум. В `cb_recipe`
сначала проверяем кэш через существующий `repositories.get_recipe` и показываем
оценку только когда рецепта нет. Одна дешёвая выборка на нажатие.

## Тестирование

**Unit**

- правила выхода и удаления: единственный админ не может уйти; админ не может
  удалить админа; админ не может удалить себя кнопкой; чужой `member_id`
  отвергается; `invite_code` обнуляется при уходе последнего участника;
- `split_for_telegram`: короткий текст остаётся одним куском, длинный режется
  по границам строк, ни один кусок не превышает лимит, строка длиннее лимита не
  зацикливает;
- полнота `LLM_WAIT_HINTS`: гард-тест — у каждой операции, на которую есть
  плейсхолдер, есть подсказка;
- счёт попыток онбординга, включая переход через UTC-полночь.

**Integration**

- обработчик ошибок: юзер получил сообщение, суперадмин получил алерт, второй
  такой же алерт подавлен дросселем, безобидная ошибка Telegram алерт не
  вызывает;
- удаление участника и самовыход через хендлеры, с проверкой уведомлений.

Существующий гард-тест на «ё» в `bot/` и `core/` новые тексты обязаны пройти.

## Что в этот заход НЕ входит

Осознанно отложено (из того же аудита, отдельными задачами):

- единый `LLMClient` на процесс вместо создания на каждый вызов;
- `timeout` / `max_retries` на `AsyncAnthropic`;
- защита от двойного тапа на кнопках генерации;
- персистентный FSM-storage вместо `MemoryStorage`;
- дедупликация рассылок планировщика в БД;
- уведомление об истечении подписки;
- удаление данных по запросу пользователя.
