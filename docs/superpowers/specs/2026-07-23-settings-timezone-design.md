# Смена таймзоны семьи в /settings — дизайн

Дата: 2026-07-23. Статус: одобрено пользователем (чат).

## Зачем

Таймзона семьи определяется один раз в онбординге по городу и дальше меняется
только руками в БД. От нее зависят утренний дайджест и напоминание «пора
планировать». Семьям нужен способ поменять зону изнутри бота — переезд,
неверно распознанный город, старый сид.

## UX-флоу

1. В /settings — третья кнопка «Таймзона» (callback `set:tz`), рядом с
   «Дайджест вкл/выкл» и «Час дайджеста». Текущая зона уже показывается
   в тексте /settings — остается.
2. Тап по кнопке → ForceReply «Напишите ваш город (например: Москва, Дубай)»
   (FSM-состояние).
3. Юзер пишет город → LLM определяет IANA-зону → зона валидируется через
   `ZoneInfo` → сохраняется сразу (без экрана подтверждения).
4. Ответ: «Таймзона обновлена: Asia/Yekaterinburg (у вас сейчас 14:32)» +
   возврат постоянной reply-клавиатуры `kb_main()` (паттерн коммита 3613a1f —
   ForceReply вытесняет ее). Локальное время — самопроверка юзера: если не
   его, город распознан неверно, можно повторить.
5. Город не распознан / LLM вернул мусор / невалидная IANA → «Не узнал город,
   попробуйте иначе (например: Москва, Дубай)», состояние сохраняется —
   можно сразу написать другой город.
6. Ошибка LLM (LLMError) → дружелюбная ошибка, состояние очищается.

## Права и границы

- Только админ семьи: `IsAdmin()` на хендлере кнопки (существующий catch-all
  `set:*` из этапа 4 даст не-админу alert «Настройки меняет администратор
  семьи»).
- Команды в text-состоянии не проглатываются: фильтр `~F.text.startswith("/")`
  (паттерн этапа 3, как в custom_date/replace_hint).
- Пустой/нетекстовый ввод в состоянии — тот же ответ «Не узнал город...».

## Механика распознавания

- Одна сервисная функция `family_service.change_family_timezone(session, *,
  family, city, llm=None) -> str | None` (рядом с `update_digest_settings` —
  настройки семьи живут там): лимиты → LLM → валидация → запись → usage.
  None — город не распознан, таймзона не тронута.
- Мини-промпт `core/prompts/timezone_detector.md` по паттерну остальных
  промптов. LLM отвечает строго JSON `{"timezone": "<IANA или null>"}`.
- Валидация ответа: `ZoneInfo(tz)` (не распозналась — как «не распознан»).
  Один автоматический retry на невалидный JSON — как в generate_profile.

## Лимиты и учет

- Перед LLM-вызовом: `ensure_within_limits(operation="tz_detect")` — в
  триал-словаре ключа нет, значит проверяется только месячный токен-потолок
  (защита от спама; триал-счетчика у операции нет намеренно).
- После вызова: `log_llm_usage(operation="tz_detect")` — расходы видны
  в /admin.
- Отказ потолка → `denial_text(e)` (kb «Хочу подписку» по общему правилу
  этапа 4: только если подписки нет).

## Хранение

`families.timezone` — существующая колонка, миграций нет. Запись делает
`change_family_timezone` (мутация family + flush, по образцу
`update_digest_settings`; ее саму не расширяем — разные настройки,
разные хендлеры).

## Что НЕ делаем (YAGNI)

- Не трогаем profile_md (город в профиле — вкусовой контекст, не время).
- Без пресетов-кнопок, без экрана подтверждения, без уведомления семье.
- Без смены зоны в онбординге (там уже есть — по городу из анкеты).

## Тесты

- Unit: кнопка «Таймзона» в клавиатуре /settings; не-админ на `set:tz` →
  alert (покрыто catch-all, регрессионный ассерт); хендлер города: успех
  (сохранение + текст с локальным временем), не распознан (состояние
  живо), LLMError (состояние очищено); команда в состоянии не съедается.
- Integration: `detect_timezone` с FakeLLM — валидная зона, `null`,
  невалидная IANA («Europe/Mordor» → None), retry на мусорный JSON;
  запись usage `tz_detect`; обновление `families.timezone` в БД.
