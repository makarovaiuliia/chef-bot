# Аналитика беты: события воронки — дизайн

Дата: 2026-07-23. Статус: одобрено пользователем (чат).

## Зачем

Первая внешняя когорта невоспроизводима. Если она пройдет онбординг без логов,
мы не узнаем, где она сыпалась, а повторить набор с теми же людьми нельзя.
Сейчас нет способа отличить «семья не дошла до меню» от «семья дошла и не
вернулась».

Врезка между Task 8 и Task 9 (Task 8.5) — до прихода внешних семей, не после.

## Границы

В спеке — запись событий и минимальный readout, без которого логирование
остается write-only.

Осознанно НЕ входит (отдельным заходом, после того как когорта под наблюдением):

- `/families` отдельной пагинированной командой — `/admin` уже печатает список
  семей, для когорты из горстки семей пагинация избыточна.
- `/say` — первую когорту набирали руками, связь с ней есть вне бота; плюс это
  дверь к рассылкам, а рассылка без opt-out кончается жалобами на бота.
- Опрос после первого меню — единственное, что меняет UX; «почему отвалился»
  у горстки первых семей узнается прямым разговором.
- Событие `sub_requested` — таблица `subscription_requests` уже считает спрос,
  `/admin` уже показывает «Заявок: N».
- `core/texts.py` — в этой части нет новых пользовательских текстов.

Схема событий общая: все перечисленное добавляется новыми типами без миграций.

## Модель данных

Миграция `0008`.

```
events
  id          PK
  family_id   FK families, nullable, index
  user_id     BigInteger, nullable, index
  type        String(64), index
  payload     JSON nullable
  created_at  timestamptz (CreatedAt)
  index (family_id, created_at)

families
  + last_active_at  timestamptz nullable
```

Обе ссылки nullable, потому что события бывают двух природ:

- шаги онбординга случаются до создания семьи — есть `user_id`, `family_id` NULL;
- `limit_hit` возникает в сервисе лимитов, которому актор не передается — есть
  `family_id`, `user_id` NULL.

Инвариант «хотя бы одно из двух заполнено» держим кодом, без CHECK-констрейнта
(портируемость SQLite/Postgres).

`last_active_at` — денормализация ради списка семей в `/admin`: считать
`MAX(created_at)` по всей таблице событий на каждый показ списка дорого.

В `payload` пишем только перечислимые значения. Никакого пользовательского
текста — иначе таблица событий незаметно превращается в хранилище персональных
данных о питании.

## Слой записи

`core/analytics/events.py`.

- `async def log_event(*, family_id, user_id, event_type, payload=None) -> None`

  Открывает собственную короткую `session_scope()` и коммитит независимо от
  бизнес-транзакции. В той же сессии обновляет `families.last_active_at`, если
  `family_id` задан. Целиком обернут в `try/except` с `logger.warning`: падение
  аналитики не имеет права сломать генерацию меню.

  Параметр назван `event_type`, а не `type` — не перекрываем builtin; колонка
  в БД остается `type`.

- `async def log_first_menu_generated(*, family_id, user_id) -> bool`

  Идемпотентно: проверяет наличие `first_menu_generated` у семьи и вставляет,
  только если его нет. Возвращает признак «это первое меню семьи». Возврат
  сейчас не используется — это готовый гейт для опроса из будущей части 3.
  Гонка двух одновременных генераций теоретически даст дубль; для воронки это
  приемлемо, уникального индекса не ставим.

Типы событий — константы (`StrEnum EventType`) в том же модуле, чтобы опечатка
не создавала новый тип молча. Хранятся строкой в `String(64)`, не как DB-enum:
новые типы должны добавляться без миграций.

Отдельная сессия — сознательный выбор при Postgres в проде: MVCC, два соединения
пишут не мешая друг другу. Побочный эффект: событие может пережить бизнес-операцию,
которая упала. Для воронки это приемлемо, для биллинга было бы нет.

## Типы событий и точки записи

| тип | где пишется | family_id | user_id |
| --- | --- | --- | --- |
| `onboarding_step_1`…`_6` | `bot/handlers/onboarding.py` | NULL | есть |
| `onboarding_profile_failed` | `bot/handlers/onboarding.py` | NULL | есть |
| `onboarding_completed` | `bot/handlers/onboarding.py` | есть | есть |
| `first_menu_generated` | `bot/handlers/plan.py` | есть | есть |
| `limit_hit` | `core/services/limits.py` | есть | NULL |

Маппинг шагов — ровно по нумерации, которую видит юзер («N/6» в текстах):

1. состав семьи выбран (`on_household`)
2. приемы пищи подтверждены (`on_slot`, ключ `done`)
3. ограничения подтверждены (`on_restriction`, ключ `done`)
4. время готовки выбрано (`on_cook`)
5. предпочтения подтверждены (`on_pref`, ключ `done`)
6. «что еще важно» отправлено или пропущено (`on_extra_text` / `on_extra_skip`)

Вопрос про город в UI не нумерован («И последнее») и отдельным шагом не пишется:
отвал на нем виден как «есть `step_6`, нет ни `completed`, ни `profile_failed`».

`onboarding_profile_failed` — ветка `except LLMError` в `_generate_and_show`.
Это главная точка отвала, которую иначе не отличить от «бросил на вопросе».

`onboarding_completed` — после `create_family` в `on_profile_ok`. Первое событие
с `family_id`: оно же связывает `user_id` с семьей.

Один юзер может попасть и в `profile_failed`, и затем в `completed` (перезапустил
и дошел). Воронка считает уникальных юзеров, так что это ее не ломает, а дает
полезное «сколько пережило сбой генерации».

`limit_hit` — в `ensure_within_limits` перед обоими `raise`. Payload:
`{"operation": <op>, "kind": "trial"}` и
`{"operation": <op>, "kind": "monthly_cap", "subscribed": <bool>}`. Одна точка
покрывает все операции (menu_gen / replace / recipe / shopping / tz_detect).

`first_menu_generated` — в `_generate_and_show` после успешного
`menu_planner.generate_menu`, то есть в момент первого показа драфта. Именно
драфт, а не подтверждение: сегмент «сгенерил и не вернулся» — как раз тот,
который надо видеть, а по подтверждению он невидим. `_generate_and_show`
вызывается и при регенерации — идемпотентность `log_first_menu_generated`
это гасит.

## Где вызываются

Правило «события пишут сервисы, а не хендлеры» держим там, где сервис есть:
`limit_hit` уходит в `core/services/limits.py` и одной точкой покрывает всех
вызывающих.

Шаги онбординга — осознанное исключение: онбординг это чистый FSM в
`bot/handlers/onboarding.py`, у шагов нет сервисного слоя, каждый шаг —
переход состояния и `state.update_data`. Писать их неоткуда, кроме хендлера.
`first_menu_generated` тоже пишется из хендлера: сервис `generate_menu` не знает,
что показ драфта состоялся.

## Readout

Без чтения логирование бесполезно. Минимальный readout — в существующем
`/admin`, отдельной командой не обрастаем.

1. Блок воронки: `COUNT(DISTINCT user_id)` по каждому типу, за все время.
   Считаем уникальных юзеров, а не события: перезапуск онбординга иначе надувает
   верх воронки.

   ```
   Онбординг:
     1. состав: N
     2. приемы: N
     3. ограничения: N
     4. время: N
     5. предпочтения: N
     6. дополнения: N
     профиль не создался: K
     семья создана: M
     первое меню: F
   ```

   За все время, а не за календарный месяц (в отличие от остальной сводки
   `/admin`): онбординг случается с юзером один раз, месячное окно его режет.

2. Колонка `last_active` в существующем списке семей `/admin`.

Выборка — `core/services/admin_reports.py`, возвращает dataclass'ы;
форматирование — в `bot/handlers/admin.py`. Воронка считается через
`GROUP BY type`: типы шагов сделаны отдельными строками именно ради этого —
запрос по JSON-полю пришлось бы ветвить под SQLite и Postgres.

## Тестовая инфраструктура (обязательный пункт)

`tests/conftest.py` поднимает приватный engine на `sqlite+aiosqlite:///:memory:`.
У SQLite `:memory:` каждое соединение — отдельная пустая БД, поэтому `log_event`
со своей сессией через глобальный engine попал бы в БД без схемы, получил
`no such table: events`, и его собственный `try/except` это проглотил бы. Итог
был бы худшим из возможных: зеленые тесты и ноль телеметрии.

Правка: фикстура `db_session` переводится на временный файл SQLite (`tmp_path`)
и инициализирует глобальный engine/sessionmaker `core.db`, отдавая сессию из
него же. Тогда `log_event` пишет в ту же БД, и путь кода в тестах тот же, что
в проде.

Остаточное ограничение SQLite: если бизнес-сессия держит незакоммиченную запись,
второй писатель блокируется (в Postgres такого нет). Это задевает
`first_menu_generated` и `onboarding_completed` — там до вызова уже есть
незакоммиченные записи. Правило для тестов: события проверяем после коммита
бизнес-транзакции, а не в середине нее.

## Тесты

- Unit `log_event`: пишет событие; обновляет `last_active_at`; при
  `family_id=None` семью не трогает; при исключении внутри — наружу не
  пробрасывает и логирует предупреждение.
- Unit `log_first_menu_generated`: первый вызов вернул True и вставил, второй
  вернул False и дубль не создал.
- Unit `admin_reports`: воронка считает уникальных юзеров (два `step_1` от
  одного `user_id` дают 1); пустая база дает нули.
- Integration онбординг: полное прохождение пишет `step_1..6` и `completed`
  с `family_id`; падение генерации профиля пишет `profile_failed`.
- Integration лимиты: исчерпанный триал пишет `limit_hit` с `kind="trial"` и
  нужной операцией; месячный потолок — с `kind="monthly_cap"`.
- Integration plan: первая генерация драфта пишет `first_menu_generated`,
  регенерация его не дублирует.
- Регрессия: сбой записи события не ломает бизнес-флоу — генерация меню доходит
  до конца при падающем `log_event`.
